# セキュリティ設計

最重要要件: 「セキュリティリスクをゼロにする」のではなく、現実的に可能な範囲で
攻撃面を最小化する。

## ネットワーク境界

- ルーターのポート開放を行わない。
- NAS・社内PCをインターネットへ公開しない。
- 社内PCはGoogle API（Sheets/Drive）へのアウトバウンドHTTPS、NASへのアウトバウンド
  SMB（イントラネット内）のみを発信する。待受ポートは一切開かない。
- 外部（Google/インターネット）から社内ネットワークへ接続を開始する経路は存在しない
  （すべて社内PC発の接続）。

## 認証情報の管理

- サービスアカウント鍵ファイル・SMB認証情報・スプレッドシートID等は、すべて
  環境変数（`.env`、`.env.example`にキー一覧のみコミット）または
  OS資格情報ストア経由で取得する。ソースコードへのハードコードは禁止。
- GAS側の秘匿値（DriveフォルダID・SlidesテンプレファイルID等）は
  `PropertiesService.getScriptProperties()` で管理し、ソースへ直書きしない。
- 社内PCのOS種別は未確定（要確認）だが、Python `keyring` パッケージ
  （Windows Credential Manager / macOS Keychain / Linux Secret Service いずれにも
  対応）でOS資格情報ストアを抽象化する方針を採用し、OS確定前でも実装を進められる
  ようにする。特にSMBパスワードは、`.env`への平文格納より`keyring`経由での取得を
  優先する（`SMB_CREDENTIAL_KEY`のようなキー名だけを`.env`に置き、実値は
  `keyring`から引く構成を推奨）。OS確定後、具体的なストア実装を選定する。

## パストラバーサル対策

`python/autohp/path_safety.py` を、NASパスを組み立てる唯一の窓口とする。

1. 建物名・部屋番号・ファイル名などスプレッドシート由来の各セグメントを
   ホワイトリスト正規表現で検証し、一致しなければファイルシステム操作を
   一切行わずに例外を送出する。
2. `.` / `..` の単独セグメントは明示的に拒否する。
3. セグメント結合後のパスを正規化し、許可ルート（`募集用` / `マイソク` 等）配下に
   収まっているかを「区切り文字を含めた前方一致」で検証する
   （単純な文字列前方一致だと `募集用_evil` のような兄弟ディレクトリを
   誤って許可してしまうため）。
4. `smb_client.py` は検証済みの `SafePath` 型のみを受け取り、生の文字列パスを
   受け付けない。これにより、将来の実装追加時にサニタイズをうっかりバイパス
   することを型レベルで防ぐ。

境界値のテストは `python/tests/test_path_safety.py` に実装済み
（`..`、パス区切り混入、NUL文字、絶対パス等の拒否を確認）。

## 最小権限のNASアカウント

- 汎用/管理者アカウントを使わず、マイソク自動生成専用のNASアカウントを作成する。
- 権限は `募集用`（読取専用）・`マイソク`系出力先（読書き）にのみ限定し、
  それ以外の共有・フォルダへはアクセスできないようにする。
- SMBの匿名/ゲストアクセスは無効化し、NASが対応していればSMB署名を有効化する。
- 要確認: 実際のNAS製品（Synology/QNAP/Windows Server等）に応じた具体的な
  共有ACL設定手順。

## 任意コード実行の防止

- `subprocess` / `eval` / テンプレート駆動のコード実行を一切行わない。
- テンプレート設定（YAML）はpydanticでデータとしてのみパースし、実行しない。
- 画像合成はPillowの描画APIのみを使用する。

## エラー出力の取り扱い

- スプレッドシートへ書き戻す `error_message` は、例外の種類ごとに用意した
  固定の日本語メッセージ（`autohp.errors.AutoHPError.user_message`）のみを使う。
  内部パス・認証情報・スタックトレースは絶対に含めない。
- 詳細情報（`detail`、スタックトレース等）はローカルのログファイルにのみ出力する
  （`python/autohp/logging_setup.py`）。

## ログ

- 構造化JSON形式でローカルファイルへ日次ローテーション出力する
  （保持日数は`python/autohp/config.py`の`log_retention_days`、デフォルト30日を
  正式デフォルトとして採用。運用開始後に実測して調整する）。
- 各ログ行に `job_row_id` / `worker_id` / `stage` を付与し、ジョブ単位での
  追跡・障害調査を可能にする。

## ポーラーの稼働台数

`docs/architecture.md`の「ジョブ状態管理」節のとおり、ポーラーは単一PCでのみ
稼働させる運用を正式方針とする。楽観的クレーム（Sheets APIにCAS相当の
プリミティブがないための擬似排他）は複数PC同時稼働を想定した完全な排他制御では
ないため、複数PCでの同時稼働が必要になった場合は、その時点で真の排他制御
（単一デザインポーラーへの一本化、または別途ロック機構の追加）を再検討すること。

## API公開について

本設計では新規の外部API公開を行わない（GAS↔社内PCはSheets/Driveのポーリング
経由）。将来的にどうしても外部APIが必要になった場合は、以下の観点で
代替案との比較検討を行い、本ドキュメントに追記すること: なぜ必要か、
Sheets/Driveポーリングで代替できない理由、認証方式、公開範囲の最小化策。
